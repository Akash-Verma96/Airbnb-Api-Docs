Airbnb Backend Docs

    
A production-style microservices backend for hotel inventory management, room booking, and transactional email notifications. Built with Node.js, TypeScript, Go, MySQL, Redis, and BullMQ.


    

      

        
Architecture

        
Microservices

Auth

        
None (v1)

JSON

      BookingService :3002
      NotificationService (Worker)
      AuthInGo (Go)
    

  


  
  

    
Architecture

    
Three independently deployable Node.js services communicate via HTTP (BookingService → HotelService) and an async BullMQ queue (BookingService → NotificationService via Redis).


    
┌───────────────────────────────────────┐
│           Client Application          │
└──────────────┬────────────────────────┘
               │
   ┌───────────┴───────────┐
   │                       │
┌──▼──────────────┐  ┌─────▼──────────────┐
│  HotelService   │◄─│  BookingService     │
│  Port: 3001     │  │  Port: 3002         │
│  Sequelize+MySQL│  │  Prisma+MySQL       │
└─────────────────┘  └────────┬───────────┘
   │ BullMQ                   │ Redlock
┌──▼──────────────┐  ┌────────▼───────────┐
│ Redis + BullMQ  │  │  Redis (Redlock)    │
└──────┬──────────┘  └────────────────────┘
       │
┌──────▼──────────┐  ┌────────────────────┐
│ RoomGen Worker  │  │ NotificationService │
└─────────────────┘  │ (Mailer Worker)     │
                     └────────────────────┘


    
Inter-Service Calls

    
BookingService makes synchronous HTTP calls to HotelService during the booking flow using Axios. The base URL is configured via HOTEL_SERVICE_URL.


    

      
sequence — create booking

      
Client → POST /booking
  BookingService → acquire Redlock (hotel:<id>)
  BookingService → GET /rooms/getAvailableRooms   (HotelService)
  BookingService → INSERT Booking (PENDING)
  BookingService → POST /rooms/update-rooms-id    (HotelService)
  BookingService → release lock
Client ← { bookingId, IdempotencyKey }

Client → POST /booking/confirm/:key
  BookingService → SELECT ... FOR UPDATE (idempotency row)
  BookingService → UPDATE Booking SET status=CONFIRMED
Client ← { bookingId, status: "CONFIRMED" }

200Successful GET / POST / PATCH operations

Hotel Service · Scheduler

    
Scheduler Endpoints

    
HotelService runs a node-cron job (default: 0 2 * * * — 2 AM UTC) to extend room availability by one day for every room category. These endpoints manage it at runtime.


    

      

        POST
        /api/v1/scheduler/start
        Starts the cron scheduler. No-op if already running.
      

      

        

          
json — 200 OK

          
{ "message": "Room availability extension scheduler started successfully", "success": true, "data": { "status": "started" } }

        

      

    

  


  

    

      

        POST
        /api/v1/scheduler/stop
        Stops the running cron scheduler and clears the internal task reference.
      

      

        

          
json — 200 OK

          
{ "message": "Room availability extension scheduler stopped successfully", "success": true, "data": { "status": "stopped" } }

        

      

    

  


  

    

      

        GET
        /api/v1/scheduler/status
        Returns whether the cron scheduler is currently active.
      

      

        

          
json — 200 OK

          
{ "message": "Scheduler status retrieved successfully", "success": true, "data": { "isRunning": true } }

        

      

    

  


  

    

      

        POST
        /api/v1/scheduler/extend

json — 200 OK

          
{ "message": "Manual room availability extension completed successfully", "success": true, "data": { "action": "manual_extension_completed" } }

Notification Service · Background Worker

    
Worker Overview

    

      📭
      The NotificationService does not expose public-facing HTTP API endpoints. It is a background worker that consumes BullMQ jobs from Redis and sends transactional emails via Nodemailer + Handlebars.
    


    
BookingService ──► Redis (mailer-queue)
                           │
              NotificationService Worker
                           │
                  renderMailTemplate()  ← Handlebars (.hbs)
                           │
                    nodemailer.sendMail()
                           │
                    SMTP (Gmail / custom)


    
Worker Behaviour

    

      
EventAction

      
        
Job "payload:mail" receivedRender Handlebars template → send via Nodemailer

        
Job name mismatchThrow Error("Invalid job name") → job marked as failed

        
Nodemailer errorThrow InternalServerError → job retried per BullMQ policy

        
completedLog success

        
failedLog "Email processing failed!"

      
    

  


  

    
Queue Job Schema

    
Jobs are added via addEmailToQueue(). The payload conforms to NotificationDto:

    

      
typescript

      
interface NotificationDto {
  to: string;               // Recipient email address
  subject: string;          // Email subject line
  templateId: string;       // Handlebars template identifier (e.g. "welcome")
  params: Record<string, any>;  // Template variable substitutions
}

    

    

      
json — example payload

      
{
  "to": "guest@example.com",
  "subject": "Your Booking Confirmation — The Grand Horizon",
  "templateId": "welcome",
  "params": {
    "name": "Alex",
    "appName": "Booking App"
  }
}
